## MINING 局间热更新入口

双击项目根目录 `start_mining_hot.cmd`。入口会复用有效的 MINING 人工通道，或打开任务终端，再启动独立的自主 AI。采集与控制器连接保留；每局结束释放输入，下一局用全新进程导入最新识别、策略和模型代码，并重新读取 `profiles/mining.supervised.local.json` 与 `profiles/mining.ai.local.json`。本局输入版本固定，修改在下局生效。

## 先确认画面和控制通路

此前接入检查枚举到 `Hagibis` 采集设备、`USB-Enhanced-SERIAL CH343 (COM5)`，并已安装 `pyserial 3.5`。当时约 30 秒的只观察测试取得 1920×1080、约 60 fps 的采集数据，接口取图成功，录像队列写入 1,729 帧且未报告队列丢帧，但画面为黑屏，没有取得实机运动参数。这是历史检查结果；本次实验的画面和连接状态应以 GUI 当前显示为准。

NS 进入四项小游戏选择页后，双击项目根目录的 `start_live.cmd`，或 `scripts/open_task_terminal.cmd`，打开图形任务终端。这两个入口复用本项目已有的 GUI，不再在命令行要求输入游戏编号。脚本优先使用 `F:\Anaconda3\pythonw.exe`。

窗口中的“采集卡与控制器”按旧项目任务终端组织：上行设置采集后端、设备、分辨率和 FPS；下行设置 EasyCon 串口及控制连接。选择游戏、任务模式和轮数后点击“开始任务”，才启动本次实机任务；打开窗口本身不会开始游戏或发送配对序列。默认参数为设备 0、COM5、1920×1080、60 fps、DSHOW，均应根据本机实际情况核对。

只需从命令行打开同一 GUI 时运行：

```powershell
python run.py task-terminal
```

若旧的黑色命令行窗口仍在运行，先在旧窗口按 Ctrl+C，等待释放 COM5 和采集卡，再开始 GUI 中的任务。不要同时开两个实机任务争用相同设备。

首次使用先选“人工调试”。只想检查画面时取消“启用控制”，再点击“开始任务”。“仅游戏内录像”控制画面落盘，不影响预览与按键日志。需要测试输入时，停止只观察任务，再启动一个启用控制的人工任务，并打开独立的“手柄调试”窗口。虚拟按键和左右摇杆放在这个调试窗口内，沿用旧项目调试界面的分组；它共享当前任务的控制通道，不另开同一个串口。

启动后先核对截图确实来自 NS。电脑端手柄沿用旧项目 EasyCon 方案；板子与主机的连接按现有固件方案处理。本项目没有实现仅靠 Windows 虚拟手柄直接控制 NS 的新协议。只有主机实际响应 A、方向键、双摇杆之后，才能继续标定。

## 四个选项是任务模式，不是四套标定算法

“小游戏”选择 MINING、HOPPING、JUGGLING、LANDING；“模式”决定本次做什么。这两个选项相互独立，只有“Retry 参数标定”会采样并拟合动作响应。

| 模式 | 使用场景 | 按下开始后的行为 | 停止位置 |
|---|---|---|---|
| 人工调试 | 首次检查画面、菜单识别、按键和摇杆响应 | 持续采集与记录，等待“手柄调试”窗口或助手接口的短时输入；不自动选游戏、不运行游戏 AI | 点击停止后保持当前游戏页面并释放输入 |
| 仅定位菜单 | 验证菜单光标识别和上下导航 | 从四项选择页移动到指定小游戏高亮，不按确认开局 | 四项选择页的目标选项 |
| 单局后返回 | 已校准后运行普通游戏 AI | 进入指定游戏，运行一局，结算后选 QUIT | 确认回到四项选择页后停手 |
| Retry 参数标定 | 建立实机输入到运动的响应数据 | 进入指定游戏，发送独立短脉冲探针，结算后 RETRY，按回合拟合和验证 | 达到轮数或模型验证门槛后，在结果页停手 |

表中的自动输入需要“启用控制”及相应配置门槛。“标定轮数”只用于最后一个模式：`3` 表示最多采三轮，`0` 表示持续 Retry，直到模型达到配置的验证门槛或人工停止。“采满三轮”不等于“参数拟合成功”。

## 第一次实机适配的操作顺序

1. 在 NS 停到四项小游戏选择页，在 GUI 选择本次适配的小游戏和“人工调试”，核对采集参数与串口，启动任务。
2. 看预览确认游戏区裁剪正确；在独立“手柄调试”窗口逐次测试 A、方向键和左右摇杆，观察 NS 的实际反馈。自动流程暂停仅暂停软件，不会自动暂停 NS。
3. 保存实时截图，核对 `menu:*`、`countdown:*`、`result:retry/quit`。复制并校准本地菜单配置，步骤见下文；识别为 unknown 时先查画面、裁剪和模板，不把 unknown 当作游戏结束。
4. 停止人工任务，选择“仅定位菜单”并加载本地菜单配置。确认它能逐项移动到目标高亮并停手，再进入参数标定。
5. 在本地配置中启用独立探针，选择“Retry 参数标定”，先设 `3` 轮。查看 `calibration_samples.jsonl` 和 `motion_fit.json` 中的样本覆盖、拒绝原因、训练误差和留出误差。
6. 确认识别与输入记录可靠后，可把轮数设为 `0` 持续采样。通过有限横向模型的验证后仍需独立应用验证，不能直接把游戏 profile 改成“已完整校准”。

## 助手调试接口

每次运行创建独立 `artifacts/live-...` 目录；其中 `control_endpoint.json` 保存本次本机地址与随机令牌，`artifacts/control_endpoint.json` 为最新运行的发现入口。令牌不需要粘贴到聊天；客户端会自行读取。

```powershell
python tools/live_client.py status
python tools/live_client.py frame --output artifacts/current-ns.png
python tools/live_client.py pause
python tools/live_client.py press --buttons DPAD_DOWN --duration 0.08
python tools/live_client.py release
python tools/live_client.py resume
python tools/live_client.py events
```

手动摇杆示例：`press --left-x 12000 --duration 0.12`，右摇杆用 `--right-x`。需要指定某次运行时，在子命令前加 `--session <本次运行目录>`。

`pause` 暂停软件自动流程，**不等于暂停 NS 游戏**。手动短按要求先暂停自动流程；HTTP 线程只排队，实际发送统一经过主控制循环。`release` 同时暂停自动流程，避免马上又被自动按键覆盖。`resume` 先松开，再恢复观察与自动流程。GUI 的“停止任务”结束采集与记录并尝试释放输入；保留的命令行 `live` 入口使用 Ctrl+C 停止。

接口仅监听本机，兼容旧项目的 `GET /status`、`GET /frame?kind=capture`、`POST /commands`、`GET /commands/<id>`；另有 `/frame.png`、`/events` 及直接暂停/控制端点。终端当前发布原始采集截图和分析状态，未发布 `kind=analysis` 标注图。PNG 只在请求取图时编码，录像编码也在独立线程中执行。

独立虚拟手柄按鼠标按下/松开事件更新完整状态，不等待“点击完成”。按住时每 50 ms 续一个 150 ms 的 `state` 租约，更新摇杆或组合键不插入归中帧；松开、关闭或失焦时释放。助手可使用 `/commands` 的 `command: state` 更新同一通道，原有 `press` 仍用于一次短按。HTTP 客户端应复用 opener/连接设置，避免客户端初始化耗时导致租约过期。

一次真实 NS 结算页测试中，约 0.675 秒内发送了 40 个连续非零摇杆报告，中间无归中报告，释放后为零。该结果仅验证发送保持，不能代替游戏中运动模型的测量；证据在 `artifacts/supervised-mining-input/continuous-hold-recheck.json`。

## 菜单验证与两种自动任务

菜单状态机按实际画面闭环处理：观察当前高亮项 → 上下逐项移动 → 确认目标 → 开局倒数期间松开输入 → 游戏运行 → 识别结果页。

参考画面中的四项为竖排；结果页有 `RETRY / QUIT`，选择页的 `B Exit` 是退出整个游戏机。[1] 当前菜单上下键、确认 A、短按时长是待实机确认的配置，不能把参考画面推断当成输入实测结果。

先复制 `profiles/session.json` 为 `profiles/session.local.json`，在人工调试中逐项核对 `menu:*`、`countdown:*`、`result:retry/quit` 的识别及按键反馈。必要时从实时截图重做 `assets/session` 的模板和 ROI。确认后把**本地 session** 的 `calibrated` 标记设为 `true`，并在 GUI 的“菜单/标定配置”中选择它。该标记用于菜单校准门槛，不表示任何游戏动力学已经标定；游戏 profile 的完整校准状态仍独立。

GUI 中选择“仅定位菜单”可只验证目标高亮，不确认开局。以下命令行等价入口保留供调试使用：

```powershell
python run.py live --game juggling --mode menu --session profiles/session.local.json --port COM5 --control
```

GUI 中选择“单局后返回”、加载已校准的游戏配置；该模式在结算后选 QUIT、确认回到四项选择页后停手。命令行等价入口：

```powershell
python run.py live --game juggling --mode single --session profiles/session.local.json --profile profiles/juggling.local.json --port COM5 --control
```

`single` 需要该游戏已独立校准的 profile；随附参考视频 profile 的 `advisory_only` 会阻止普通游戏 AI 控制。首次实验不应靠改标志冒充校准完成，应先使用 `manual` 和独立探针模式建立数据。

## Retry 标定模式

在本地 session 中把 `calibration.enabled` 设为 `true`，核对脉冲幅度、时长、边界和拟合阈值。GUI 中选择“Retry 参数标定”，选择本地菜单/标定配置，轮数先设为 `3`，再点击“开始任务”。命令行等价入口：

```powershell
python run.py live --game juggling --mode calibrate --session profiles/session.local.json --port COM5 --control --rounds 3
```

标定模式从选择页进入目标游戏，用独立探针代替普通游戏 AI。探针使用分档左右短按和中立间隔；Juggling 依次激励两个角色。Hopping 的 B 和 Landing 的喷射需要另外显式启用。游戏结束后选择 RETRY，继续下一轮；完成指定轮数后停在结果页。`--rounds 0` 表示持续 Retry，直到达到所配置模型验证门槛后于结果页停手，或人工停止。不能保证增加回合数一定收敛，程序不会自动放宽阈值。

拟合按发送时间和观测时间对齐，比较候选有效延迟，用位置差分得到横向速度，并拟合局部速度响应。训练与验证按完整回合或隔离时间块划分。报告包含输入增益、速度反馈、偏置、有效延迟、样本覆盖和留出误差。

四个小游戏的当前标定范围不同：

| 小游戏 | 当前可拟合或记录 | 尚未覆盖 |
|---|---|---|
| MINING | 角色的横向输入响应 | 世界纵向滚屏、完整加速/撞击与强化模型 |
| HOPPING | 机器人的横向输入响应；B 探针需另外启用 | 乌贼自由运动重力、顶球后速度及完整收益链控制 |
| JUGGLING | 左右两侧角色分别激励、分别验证；两侧都通过才算该横向模型通过 | 滑步和不同鱼种的全部运动/碰撞特性 |
| LANDING | 喷射、位置和姿态采样；喷射探针需 `enable_jets: true` | 完整转动、推力和风场耦合拟合；当前不会判为标定通过 |

MINING/HOPPING/JUGGLING 也不是一键标定所有物理参数。LANDING 当前应先用固定轮数采样、检查记录，不能使用 `0` 轮并期待尚未实现的耦合模型自动通过；若选择持续 Retry，只能人工停止。

拟合拒绝回放、未执行输入、轨迹断裂、换 ID、遮挡、缺激励和不满足留出误差的数据。人工调试会暂停自动探针，恢复时重置探针并排除紧邻人工操作的样本。实际实验期间不要同时用另一只手柄操纵角色，否则电脑记录的输入无法完整解释运动。

### MINING 的 ZR 与转向研究

用户补充的策略方向是普通路段持续 ZR，急弯时考虑松开。不能由此假定前进速度无限增长、ZR 一按就瞬间达到某个常速，或加速前后转向响应相同。当前规划器仍使用待校准的分档速度模型；新增 `mining_motion.fit_mining_motion` 是独立研究接口，尚未替代规划器。

研究会按 ZR/非 ZR 分开处理横向响应、松杆惯性，并在有可靠前进速度观测时比较恒加速度和逐渐趋于终速的候选模型。碰墙、普通撞石、强化碎石与强化开始/结束片段必须剔除或分层，不能混成普通加速度。

角色在屏幕上的 y 近似不变时，仅靠角色位置无法识别世界前进速度；需要额外可靠的滚屏、距离或其他独立速度观测。新模块在缺失时明确拒绝给出纵向参数；目前仍不知道 NS 中持续按 ZR 是否会一直增速。候选恒加速度模型即使在短片段拟合良好，也不能证明速度会无限增长。

默认误差阈值、延迟网格和动作时窗都是工程起点，尚未用 NS 数据验证。像素抖动会放大差分速度误差；某个横向模型 `passed: true` 仍不等于视觉、全游戏动力学或最高分策略已经可靠。报告始终保留 `calibrated: false`，不会自动把普通 AI 解锁为实机可用。

## 同时录像与记录按键

GUI 默认勾选“仅游戏内录像”：确认倒数或游戏运行后才开始写视频，菜单、结算和实际暂停时停止；识别到结束信号后保持停止，直到确认下一局。取消该勾选可关闭画面录像，控制和分析日志仍保存。命令行对应 `--no-record`。录像默认缩放至最多 1280×720，识别仍使用原始采集帧。

“采集帧”是实时采集序号，预览运行时会递增，不能用它判断是否录像。连接状态栏和右侧状态中的“录像：录制中／等待开局／已关闭”才是本次录制状态。相同空闲状态的 `trace.jsonl` 与 `session.jsonl` 每秒记录一次；游戏内观测与实际手柄传输日志仍保留。每次运行按启用的功能保留：

| 文件 | 内容 |
|---|---|
| experiment.json | 游戏、模式、实际使用配置、请求的采集参数与时钟定义 |
| capture.mp4 | 异步编码的采集画面，不含音频 |
| frames.jsonl | 每个录像帧对应的采集序号与单调时间；队列丢帧明确记载 |
| commands.jsonl | 电脑实际调用发送的完整按钮、双摇杆、发送前后时间、传输结果；包含看门狗归中 |
| trace.jsonl | 被分析的局面、检测目标、建议、最终控制状态、耗时 |
| session.jsonl | 菜单/游戏阶段、每轮开始结束、调试或自动输入来源 |
| calibration_samples.jsonl | 仅标定模式的已发送探针及其实际观测 |
| motion_fit.json | 每轮结束的最新拟合与留出验证结果 |
| recording-summary.json | 编码结果、写帧和丢帧计数 |

MP4 的固定帧率不是精确实验时钟；复盘时应通过 `frames.jsonl` 找到相同单调时间上的 `commands.jsonl`，不能只用播放器秒数推断按键延迟。发送成功表示电脑传输函数返回成功，不能直接证明 NS 执行成功；这需要后续画面响应佐证。接口令牌文件与实验记录分开，不需要作为分析材料发送。

重算已有实机采样：

```powershell
python tools/fit_motion.py <本次运行目录>/calibration_samples.jsonl --config profiles/session.local.json --output artifacts/refit.json
```
